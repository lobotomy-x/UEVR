## TL;DR

`uevr-mcp` is an MCP (Model Context Protocol) bridge that exposes UEVR's
runtime state to an external AI agent. It is **two pieces glued together**:

1. A **C# .NET MCP server** (`mcp-server/`) — speaks the MCP protocol to
   the AI client. Defines ~20 tool functions (`uevr_get_status`,
   `uevr_search_objects`, `uevr_lua_exec`, `uevr_chain`, etc.).
2. A **C++ UEVR plugin** (`plugin/`) — loads into the game process as a
   UEVR plugin DLL. Exposes an HTTP server + named-pipe server. The C#
   MCP server talks to the plugin over these transports to issue
   reflection queries, run Lua, etc.

Both pieces predate our luavrlib branch. The fork's job is to teach them
about the new API surface we added — `uevr.api_fast`, multistate workers,
the log channel, native TArray, the Live Function Caller, drag-drop
sources — so that an AI client using the MCP can exercise those features.

We also need this MCP working as part of our **own dev process**: while
testing the luavrlib changes interactively, having an AI assistant that
can reflect into the running game and verify state is far faster than
copying addresses out of the in-game tree by hand.

## What needs updating

### Plugin side (C++)

Currently `function_caller.cpp` and `property_reader.cpp` go through
their own reflection paths (basically reinventing what UObjectHook does
in our `src/mods/UObjectHook.cpp` already). They need to:

1. **Adopt the same FProperty handling we use.** Our `ScriptUtility.cpp`
   property dispatcher correctly handles all primitives, FName, FString,
   Object/Class, Struct (including the UE4-float vs UE5-double FVector
   detection), Enum, Bool (bitmask), Interface, TArray<T> for every
   element type, and out-params. The MCP plugin's reader is older and
   misses some of this.

2. **Expose `uevr.api_fast` to `uevr_lua_exec`.** The MCP's
   `uevr_lua_exec` runs Lua inside the game's UEVR Lua state. If the
   state was created by our LuaLoader, `uevr.api_fast` is already there
   for free — but if the MCP plugin spawns its OWN Lua state, it needs
   to do what `LuaLoader::state_post_init` does (open imgui/json/fs,
   then `bindings::open_sdk_fast`). Verify which path the plugin uses.

3. **Drop redundant TArray handling.** Wherever the MCP reads TArrays
   via its own JSON serializer, switch to letting Lua return them as
   native tables (or call into our `prop_to_object` ArrayProperty path).

4. **Mirror our function-caller param surface.** The MCP's
   `uevr_invoke_method` should be able to accept the same parameter
   types our in-tree caller supports (bool / int* / float / double /
   FName / FString / Object / Class / Vector / Vector2D / Vector4 /
   Rotator / Quat / LinearColor). Today the MCP coverage is narrower.

5. **Add tools for the new bits we added:**
   - `uevr_call_fast(addr, "actor_location_get")` → calls
     `sdk::AActor::get_actor_location` directly. Lets the AI bypass
     reflection for the hot transform getters.
   - `uevr_worker_spawn(name, source)` / `uevr_worker_send(name,
     source)` / `uevr_worker_stop(name)` — exposes the multistate
     worker API.
   - `uevr_set_shared(key, val)` / `uevr_get_shared(key)` — exposes the
     cross-state shared map (useful for the AI to coordinate with
     running scripts).
   - `uevr_mid_hook_create(addr, lua_callback_source)` /
     `uevr_mid_hook_remove(addr)` — exposes the
     `uevr.hook_create_mid` API.
   - `uevr_log_subscribe(severity_filter)` — stream spdlog output to
     the AI in near-real-time (currently the AI has no log feedback at
     all).

### MCP server side (C#)

For each new plugin tool above, add a corresponding C# tool definition
in a new `LuavrlibTools.cs`. Register in `Program.cs`. Document in
`AGENT.md` and `UEVR_GUIDE.md`.

The existing `uevr_lua_exec` doesn't need a new tool wrapper; just
update `AGENT.md`'s "Available Lua APIs" section to list the new
`uevr.api_fast.*` and `uevr.spawn_worker / send_to_worker / ...`
surface so the AI knows what to call inside `uevr_lua_exec`.

### Compatibility considerations

The MCP plugin compiles with cmkr (`cmake.toml`), same toolchain as our
main UEVR repo. That means dropping in our `bindings/SDKFast.cpp`
verbatim should work as long as the include paths line up. The plugin's
include surface for UEVR's public API is much smaller than what we use
internally (`sdk::AActor` etc. are private to UEVR), so the fork might
need to either:
- (a) Submodule-include our SDKFast under the MCP plugin's source set,
  AND submodule-include the UESDK source so the sdk types are
  available, OR
- (b) Re-export the needed `api_fast` shims from our UEVR.dll and have
  the MCP plugin GetProcAddress them at load time.

(a) is simpler if licensing allows; (b) is cleaner.

## Acceptance criteria

- AI agent can call `uevr_lua_exec("uevr.api_fast.get_actor_location(uevr.api:get_local_pawn(0))")` and get back a Vector3f tostring.
- AI agent can spawn a worker, send a benchmark, observe shared results.
- `uevr_invoke_method` accepts a `Quat` arg type and writes it to a `K2_SetWorldTransform` call without crashing.
- Log subscription delivers spdlog lines tagged `[lua]` and `[lua-worker]` to the AI client.
- Existing MCP tests still pass.
